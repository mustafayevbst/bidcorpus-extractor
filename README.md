# BidCorpus Tender Extractor

![CI](https://github.com/mustafayevbst/bidcorpus-extractor/actions/workflows/ci.yml/badge.svg)

LLM-пайплайн для извлечения структурированных полей из тендерных документов на португальском языке с оценкой качества извлечения.

**Автор:** Мустафаев Ниджат

**Дата:** 08.10.2026

## Задача

Я взял коллекцию бразильских тендерных документов и построил пайплайн, который автоматически извлекает из неструктурированного текста шесть полей:

| Поле | Что это |
|---|---|
| `customer_name` | организация-заказчик |
| `tender_number` | номер процедуры |
| `category` | предмет закупки |
| `deadline` | дата и время вскрытия конвертов |
| `requirements` | документы и требования к участникам |
| `participation_conditions` | условия участия |

Отдельно я оценил качество извлечения по метрикам exact-match и fuzzy-match.

## Источники и инструменты

- **Данные:** [BidCorpus](https://huggingface.co/datasets/tcepi/bidCorpus) на Hugging Face (конфигурация `bidCorpus_raw`)
- **Модель:** `openai/gpt-oss-120b` через Groq API
- **Python 3.11**, pandas, numpy, requests, datasets, pydantic, rapidfuzz
- **scikit-learn**, matplotlib — для EDA
- **GitHub Actions** — CI с пороговыми метриками
- **AI-ассистент:** Claude — консультации по коду, структуре пайплайна, текстам

## Данные

**BidCorpus** — открытый корпус тендерных документов из Бразилии (около 1.8 ГБ в конфигурации raw). Каждый документ — набор текстовых секций:

- `OBJETO` — предмет закупки
- `HABILITACAO` — требования к участникам
- `JULGAMENTO` — критерии оценки победителя
- `CONDICAO_PARTICIPACAO` — условия допуска
- `CREDENCIAMENTO` — правила аккредитации представителей

Я взял **50 документов** (загрузка через `datasets` в streaming-режиме, чтобы не качать весь корпус). Из них **15 размечены вручную** — это эталон для оценки.

## Архитектура пайплайна

```text
data/raw/*.json  →  src/extractor.py  →  data/predictions/*.json
сырые документы     LLM                  ответы модели
                                              ↓
data/gold.json   →  src/evaluator.py  →  метрики
эталон (15 шт)      сравнение
```

Модули:

- `src/loader.py` — загрузка BidCorpus
- `src/schemas.py` — pydantic-модель `Tender`
- `src/extractor.py` — обращение к Groq, извлечение полей
- `src/evaluator.py` — exact + fuzzy метрики
- `src/cli.py` — единый интерфейс запуска

## Разметка (gold)

15 документов я разметил вручную по 6 полям. Правила:

- Португальский язык, как в оригинале.
- Скалярные поля — одна строка или `null`.
- `requirements` и `participation_conditions` — списки строк.
- Если поля нет в тексте — `null` (или пустой список).
- В выборку я намеренно включил **2 «пустых» документа** (регламенты без полей закупки), чтобы проверить, что модель не выдумывает данные.

## Метрики

Я использовал два набора.

**Scalar (customer_name, tender_number, category, deadline):**

- `exact` — совпадение после нормализации (lowercase, без accents, без пунктуации).
- `fuzzy` — совпадение с порогом 0.85. В `rapidfuzz.token_set_ratio` шкала 0–100, порог 85 из 100.

**Lists (requirements, participation_conditions):**

- Precision, Recall, F1.
- `exact` — пересечение множеств после нормализации.
- `fuzzy` — жадный матчинг пар «эталон-предсказание» с порогом 0.85.

Итоговые метрики — macro-усреднение по 15 документам.

Случай «в эталоне null, у модели null» считается совпадением: пустое поле и пустой список обрабатываются как корректный ответ, если в тексте действительно ничего не было.

В таблице ниже я привожу только fuzzy-метрики. Полные значения, включая exact, лежат в `data/final_metrics.txt` и `data/baseline_metrics.txt`.

## Эксперименты с промптом

Промпт прошел три итерации.

**v1 (baseline):** общая инструкция «извлекай поля в JSON».

**v2:** добавил четкое определение `category` (с примерами «что ХОРОШО» и «что ПЛОХО») и инструкцию «сохраняй формулировки из текста».

**v3:** добавил уточнение для `customer_name` — восстанавливать название из контекста, если заказчик упомянут неявно (в адресе, реквизитах, названии связанного органа).

### Результаты по fuzzy-метрикам

| Поле | v1 | v2 | v3 (финал) |
|---|---:|---:|---:|
| customer_name | 0.87 | 0.73 | 0.80 |
| tender_number | 1.00 | 1.00 | 1.00 |
| category | 0.67 | 0.87 | 0.87 |
| deadline | 1.00 | 1.00 | 1.00 |
| requirements (F1) | 0.60 | 0.79 | 0.69 |
| participation_conditions (F1) | 0.52 | 0.49 | 0.62 |

**Итог:** v3 дает лучшую сумму метрик (4.98 против 4.88 у v2 и 4.66 у v1). Основное улучшение — `category` (с 0.67 до 0.87), за счет уточнения промпта.

При этом v3 не строго лучше предыдущих версий. По `customer_name` лучший результат у v1 (0.87), по `requirements` — у v2 (0.79). На 15 документах разница в 0.05–0.10 метрики лежит в пределах шума, поэтому я не стал дальше подкручивать промпт под конкретные документы: это привело бы к переобучению на выборке из 15 штук.

## Технические решения

В процессе работы я столкнулся с несколькими проблемами и решил их:

**1. Загрузка датасета без `trust_remote_code`.** Изначально `load_dataset` требовал запуска чужого Python-кода из репозитория. Я заменил его на встроенный parquet-загрузчик с `streaming=True` — безопасно и без скачивания всех 1.8 ГБ.

**2. Лимит output-токенов.** На длинных документах модель не успевала сгенерировать JSON. Я поставил `max_tokens=8192`.

**3. Rate limit 429.** На бесплатном тарифе Groq лимит 8000 TPM (tokens per minute). Я добавил retry с линейной задержкой (30/60/90/120 секунд).

**4. Кэширование предсказаний.** Если `doc_XXXX.json` уже существует — скрипт его пропускает. Экономит запросы и позволяет перезапускать пайплайн с места остановки.

**5. CI с порогами метрик.** Каждый push прогоняет `evaluator` и `check-metrics`. Если метрика упала ниже порога — CI краснеет. Пороги я установил с запасом 0.05–0.12 от текущих значений.

## Ограничения

- **Мало данных:** 15 документов, разница в 0.05 метрики — в пределах шума.
- **Португальский язык:** модель работает с ним, но сравнения с другими языками я не проводил.
- **Формулировки категорий:** модель часто дает более краткую форму, чем эталон (например, «Combustíveis» вместо «Combustíveis para viaturas»). Fuzzy-метрика ловит часть таких случаев, но не все — при сильном укорочении `token_set_ratio` падает ниже порога.
- **Юрисдикция:** все 15 документов — бразильские закупки, в основном по Lei 8.666/93 и Lei 13.303/2016, с упоминаниями Decreto 10.024/2019 и IN SEGES 03/2018. На других юрисдикциях промпт не проверялся.
- **Нет OCR:** если в датасете есть сканы, они не обрабатываются.
- **Одна модель:** сравнение с альтернативами (Llama, Qwen) не проводилось.

## Воспроизводимость

```bash
# 1. Клонировать репо
git clone https://github.com/mustafayevbst/bidcorpus-extractor.git
cd bidcorpus-extractor

# 2. Создать окружение
python -m venv .venv
.venv/Scripts/activate    # Windows
source .venv/bin/activate # Linux/Mac

# 3. Установить зависимости
pip install -r requirements.txt

# 4. Создать .env с ключом Groq
echo "GROQ_API_KEY=your_key_here" > .env

# 5. Загрузить данные
python -m src.loader

# 6. Извлечь поля
python -m src.cli extract

# 7. Оценить качество
python -m src.cli evaluate
python -m src.cli check-metrics
```

Проверить расхождения по конкретному полю:

```bash
python -m src.cli check category
```
